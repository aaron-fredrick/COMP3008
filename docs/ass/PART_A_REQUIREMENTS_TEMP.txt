1. ASSIGNMENT OVERVIEW
============================================================

A user signs in with a user ID of their own choosing and sees the channels that currently exist. The user can join an existing channel or create a channel. Inside a channel, the user participates in conversation with everyone else there, holds private conversations with individual members, and shares files with the channel.

The application is a real-time chat application for Windows, built using C#, the .NET Framework, Windows Communication Foundation (WCF), and Windows Presentation Foundation (WPF).

Part A is a group assignment for two or three members, although an individual may also work alone.

The solution must contain at least three projects:

* Chat Server: a self-hosted WCF service, for which a console application is sufficient. It holds all shared state: who is signed in, which channels exist, who is in each channel, and the files that have been shared.
* Polling Client: a WPF application providing the Section A user interface. It keeps itself up to date by asking the server for changes on a background thread. Several instances run at the same time.
* Duplex Client: a second WPF application offering the same functionality, in which the server pushes changes to the client instead. This is what Section C assesses.

Both clients connect to the same running server and share its state, so a user on the polling client and a user on the duplex client can be in the same channel and talk to each other.

Code is expected to be shared between the two clients, including the service contracts, data classes, and windows, rather than duplicated. Placing shared contracts in their own class-library project is recommended.

Sections A and B are marked on the polling client and server. Section C is marked on the duplex client. The polling client should be built first; the duplex client should be attempted once the polling client works.

2. REQUIRED FUNCTIONALITY
============================================================

A-F01 - Sign in with a user ID. The client application asks for a user ID and signs in. There is no password. If someone currently signed in is already using that ID, the client shows the reason and lets the user try another.

A-F02 - Show the current channel list and allow joining. The client application shows every channel that currently exists and lets the user join one. The list reflects channels created by other people and updates on its own.

A-F03 - Enforce at-most-one channel membership in the client workflow. A user is in at most one channel at a time and returns to the channel-list view on leaving.

A-F04 - Create a channel. The user can create a channel by giving it a name. If a channel with that name already exists, the client says so and the user chooses another.

A-F05 - Send and receive channel messages. Inside a channel the user sends messages and sees messages from every other member appear as they arrive.

A-F06 - Keep the channel member list current. The user sees a member list that stays up to date as people join and leave.

A-F07 - Do not show earlier channel messages to a late joiner. A user who joins part way through sees messages sent from that point onward; earlier messages are not shown.

A-F08 - Start private conversations. The user can select any other member of the channel and start a private conversation with them.

A-F09 - Show incoming private conversations separately. An incoming private message opens its own separate window, apart from the main conversation, which names the sender, keeps the history of that exchange between the two users, and allows a reply to be sent from within it.

A-F10 - Support multiple private conversations. Several private conversations can be open at once.

A-F11 - Share permitted files with a channel. The user can choose a text or image file, up to 2 MB, and share it with the channel.

A-F12 - Display shared files to channel members. Shared files appear to every member as clickable entries showing at least the file name and who shared it.

A-F13 - Retrieve and open shared files. Clicking a shared-file entry retrieves the file from the server and opens it.

A-F14 - Reject invalid files visibly. Files of a disallowed type or size are refused with a message the user can read.

A-F15 - Sign out at any time. Signing out is available at any time, from either view.

A-F16 - Cleanly sign out. On sign out, the client leaves any channel the user is in, releases the user ID, and shuts down cleanly.

A-F17 - Keep the polling client current without user action. The polling client uses a background thread that periodically asks the server for changes, including new messages, member lists, the channel list, and shared files, and updates the interface from what comes back.

A-F18 - Provide the two required client views and navigation. The client application has a channel-list view and a channel-conversation view, with navigation between them.

A-F19 - Provide channel-list controls. The channel-list view shows the available channels with controls to create and to join.

A-F20 - Provide channel-conversation controls and information. The channel-conversation view shows the conversation, a message box, the member list, the shared files, and a way to leave.

A-F21 - Make signing out available in both views. Signing out is available at all times, including from both required views.

Constraints and fallback stated with these requirements:

* Polling is a pull strategy and must periodically ask the server for changes.
* The polling interval is to be chosen deliberately: too frequent wastes the server and too slow makes the application feel dead.
* If background threads cannot be made to work, manual "Refresh" buttons may be used as a fallback. This is accepted, but requirements 2, 4, and 6 in Section A then score at most half marks because the interface no longer keeps itself current.
* The polling fallback does not apply to the duplex client. The duplex client must have neither a polling thread nor a refresh button.

3. ARCHITECTURE / SYSTEM REQUIREMENTS
============================================================

A-ARC01 - Build the application as a real-time chat application for Windows.

A-ARC02 - Use a client-server system. All traffic passes through the server; clients never connect directly to one another. This is not a peer-to-peer system.

A-ARC03 - Provide a Chat Server as a self-hosted WCF service. A console application is sufficient for hosting it.

A-ARC04 - The server holds all shared state, including who is signed in, which channels exist, who is in each channel, and the files that have been shared.

A-ARC05 - Provide a Polling Client as a WPF application with the Section A user interface.

A-ARC06 - The Polling Client keeps itself up to date by asking the server for changes on a background thread. Several instances run at the same time.

A-ARC07 - Provide a separate Duplex Client as a second WPF application offering the same functionality as the polling client, with the server pushing changes instead.

A-ARC08 - Both clients connect to the same running server and share its state. They must be able to have users in the same channel and communicate with each other.

A-ARC09 - The two clients must share code for service contracts, data classes, and windows rather than duplicating that code. A shared contracts class-library project is recommended, not stated as mandatory.

A-ARC10 - The server listens on a fixed address and port known to the clients. Because development is on a single machine, localhost with a fixed port is acceptable.

A-ARC11 - All state is held in server memory. No database is required, and nothing needs to survive a server restart.

A-ARC12 - The Duplex Client uses a duplex WCF channel over `netTcpBinding`.

A-ARC13 - The Duplex Client is a separate WPF application, not a switch or setting inside the polling client.

A-ARC14 - Both clients must build and run from the submitted solution.

A-ARC15 - Both clients must work against the same server without the server being restarted or reconfigured between them.

A-ARC16 - Test with one to five concurrent clients; at least three clients must run at the demonstration.

4. POLLING REQUIREMENTS
============================================================

A-POL01 - The polling client must keep itself current without the user doing anything.

A-POL02 - A background thread in the polling client periodically asks the server for changes.

A-POL03 - Polling must cover new messages, member lists, the channel list, and shared files.

A-POL04 - The polling client updates its interface from the data returned by polling.

A-POL05 - The polling interval must be chosen deliberately: polling too frequently wastes the server, while polling too slowly makes the application feel dead.

A-POL06 - If background threads cannot be made to work, manual "Refresh" buttons may be used as a fallback. Under this fallback, requirements 2, 4, and 6 of Section A score at most half marks.

A-POL07 - The duplex client must have neither a polling thread nor a refresh button.

A-POL08 - In the Duplex Client, channel list changes, member changes, messages, private messages, and shared files must all reach the client because the server pushed them; no timer, background loop, or refresh button may fetch updates in core functionality.

============================================================
5. DUPLEX / CALLBACK REQUIREMENTS
============================================================

A-DPX01 - The Duplex Client offers the user exactly the same functionality as the polling client in Section A.

A-DPX02 - The Duplex Client does not ask the server for anything on a timer.

A-DPX03 - On sign-in, the Duplex Client registers a callback with the server.

A-DPX04 - The server invokes the registered callback whenever something happens that the client needs to know about.

A-DPX05 - The duplex service contract is correctly declared with a callback contract and is hosted over `netTcpBinding`.

A-DPX06 - Clients register on sign-in.

A-DPX07 - The server tracks which callback belongs to which user.

A-DPX08 - Channel list changes, member changes, messages, private messages, and shared files reach the Duplex Client through server push.

A-DPX09 - The Duplex Client has no timer, background loop, or refresh button fetching updates anywhere in its core functionality. If some updates are pushed and others are still fetched, marks are awarded in proportion.

A-DPX10 - The server detects when a client closes, crashes, or is killed.

A-DPX11 - When a client disconnects, the server releases the user ID, removes the user from their channel, and tells the remaining members.

A-DPX12 - Pushing to a callback that has gone away must not bring down the server or block other users.

6. CHAT / CHANNEL REQUIREMENTS
============================================================

A-CHAT01 - The user signs in with a user ID of their own choosing; there is no password.

A-CHAT02 - Currently signed-in user IDs are unique. A duplicate is rejected with a reason the client can display.

A-CHAT03 - An ID is released immediately when its user signs out or disconnects and may then be taken by someone else.

A-CHAT04 - The client shows every currently existing channel and lets the user join one.

A-CHAT05 - The channel list reflects channels created by other people and updates on its own.

A-CHAT06 - A user is in at most one channel at a time.

A-CHAT07 - The server creates channels with unique names.

A-CHAT09 - The server holds the authoritative list of channels and their members.

A-CHAT10 - Inside a channel, the user sends messages.

A-CHAT11 - Channel messages are seen by every other member as they arrive.

A-CHAT12 - A user joining part way through sees messages sent from that point onward; earlier messages are not shown.

A-CHAT13 - The server delivers a channel message to every member of that channel at the time it was sent, and nobody else.

A-CHAT14 - The server keeps no message history and does not replay past messages to a user who joins later.

A-CHAT15 - The user can select any other channel member and start a private conversation.

A-CHAT16 - An incoming private message opens a separate window apart from the main conversation.

A-CHAT18 - Several private conversations can be open at once.

A-CHAT19 - A private message reaches the one named recipient and nobody else.

A-CHAT20 - The sender and recipient of a private message must be members of the same channel; the server refuses the message otherwise.

A-CHAT21 - Signing out makes the client leave any channel the user is in and releases the user ID.

A-CHAT22 - When a duplex client disconnects, the user is removed from their channel and remaining members are told.

15. AMBIGUITIES / UNCLEAR WORDING
============================================================

A-AMB01 - The polling interval must be chosen deliberately, with only qualitative guidance that too frequent wastes the server and too slow makes the application feel dead. No numeric polling interval or measurable threshold is specified.

A-AMB02 - The Duplex Client must invoke the callback "whenever something happens the client needs to know about," but the document does not define an exhaustive event list in that sentence. Section C item 2 separately names channel list changes, member changes, messages, private messages, and shared files.

A-AMB03 - The document says the Duplex Client offers "exactly the same functionality" as the polling client while also requiring that it have neither polling nor a refresh button. The scope of "same functionality" is not separately defined beyond the Section A functionality and the stated duplex restrictions.

A-AMB04 - The document requires a fixed address and port known to clients and says localhost with a fixed port is fine, but it does not specify a particular address or port number.

A-AMB05 - The document says to test with one to five concurrent clients and separately says at least three must run at the demonstration; it does not state whether the one-to-five range is a formal submission test limit or demonstration-only guidance.

A-AMB06 - The file requirement uses "text or image file" in Section A and later gives the permitted extensions. The document does not separately define whether file type is to be determined solely by extension or also by file content/MIME type.
